# Domain patterns

- **Order / payment / shipping / notification system**: see [`docs/order-system.md`](docs/order-system.md) for the full reference — state machines, creation paths, carrier integrations, email + WS dedup, critical invariants, common-task playbook. Read this first before changing anything in `order/`, `shipping_acs/`, `shipping_boxnow/`, or `pay_way/`.
- **ACS debugging**: see [`docs/acs-debugging.md`](docs/acs-debugging.md) — every ACS call is logged once (`acs_alias`, `outcome`, `duration_ms`, `http_status`, `error_message`, the voucher/pickup identifiers) and written to `AcsApiCall` by `AcsClient._call`; every pickup-list attempt leaves an `AcsPickupListRun`; the shipment admin has a Diagnostics timeline. Read it before debugging an ACS incident; credentials never reach either record.
- **Turnover report**: see [`docs/turnover-report.md`](docs/turnover-report.md) — the legal κύκλος εργασιών: goods, shipping and fees net of VAT, an order counted when it left the store (`Order.shipped_at`), less returns in the month they happened; quarter/month/week/day buckets, year-over-year, breakdowns, CSV and XLSX. `order/turnover.py` holds the one definition and the SQL, `OrderVatLine` (written at checkout by `order.vat_snapshot` from the receipt's own `order_vat_lines`) is what it reads, `Sales -> Turnover` shows it behind `order.view_turnover_report` (store ADMIN/OWNER) and the store dashboard's revenue reads the same module. Read it before adding another sales figure so the two cannot disagree.
- **Management profit report**: see [`docs/profit-report.md`](docs/profit-report.md) — net revenue (turnover) less the cost of goods sold (`OrderItem.unit_cost`, copied from `Product.cost_price` at sale), provider fees (`PaymentTransaction.fee`: Stripe balance transaction, Viva event 1799) and `Expense` rows; never an estimate, with cost and fee coverage shown. `order/profit.py` holds the definition; the profit report, the expenses and the cost price are the store OWNER's alone (`tenant.role_scopes.OWNER_ONLY_PERMISSIONS`). Read it before adding a cost or a fee input.
- **Product recommendations**: see [`docs/recommendations-engine.md`](docs/recommendations-engine.md) — typed `ProductRelation`, the strategy registry (`is_available` declines rather than returning noise), two-stage retrieval into `RecommendationCandidate`, the Greek embedding measurements and the TEI-vs-in-process decision, plan tiers, and the playbook for adding a strategy/surface/preset. Read it before touching `recommendation/`, `product/models/relation.py`, or the `cart` surface.
- **Product pricing and the EU Omnibus prior price**: see [`docs/product-pricing.md`](docs/product-pricing.md) — price spells, the frozen reduction episode on `Product`, every path that records a price change, the backfill, and the `priorPrice` / `announcedDiscountPercent` API fields. Read it before touching `Product.save`, `final_price`, VAT rates, or what a promotion does to a listed price; a price field must never change through `queryset.update()`.
- **IndexNow (`indexnow/`)**: see [`docs/indexnow.md`](docs/indexnow.md) — the per-store `INDEXNOW_ENABLED` switch (off by default), the key on `Tenant.indexnow_key` served as `indexnowKey` on `tenant/resolve` for the storefront's `/<key>.txt`, the queue the signals fill and the 30-minute task that sends one POST per store, and the protocol facts it was built from. Read it before touching how a product or post is announced.
- **Staging refresh anonymisation**: `manage.py staging_anonymise` (`devtools/anonymise/`) replaces every customer identity in a database restored from production, staging only. See [`docs/staging-anonymise.md`](docs/staging-anonymise.md). A new model must be given a `Scrub`, a `Delete` or a `NOT_PERSONAL` entry in `devtools/anonymise/rules.py`, and a new e-mail/phone/IP field a rule or a `NOT_PERSONAL_FIELDS` reason; `tests/unit/devtools/test_anonymise_covers_every_model.py` fails until you do.
- **Store settings (`core/store_settings.py`)**: read every django-extra-settings value through `store_setting(name)` / `store_settings(names)` (one `get_many` for all the names, so a payload of 28 settings is one Redis round trip), never `Setting.get` with a literal default. A missing row reads as its value in `settings.EXTRA_SETTINGS_DEFAULTS`, the one place a default lives, and an undeclared name raises. Validate a setting where it is saved (a `"validator"` path on its declaration, synced to every store on migrate by `tenant/settings_metadata.py`) instead of replacing a bad value at the read. A setting with structure is a serializer in `core/store_setting_shapes.py` (`STRUCTURED_SETTINGS`): the same class validates the save and describes the typed value `GET /settings/public` serves, so never hand-write a validator or a client parser for one (`docs/store-features.md`). Tests patch `extra_settings.models.Setting.get` or write rows, never a module's own reader.
- **Store features (`tenant/features.py`)**: see [`docs/store-features.md`](docs/store-features.md) — the one table behind `TenantConfig.features` and the 404 gates, the classification of every `*_ENABLED` setting, and the checklist for adding a feature, plus how the store admin shows a feature (`admin/features.py`: one rule, setup vs record pages, `Gate`, `FeatureInline`; a new feature-owned admin page or inline is declared there). Read it before adding a switch a client has to honour.
- **Store-editable texts (`texts/`)**: see [`docs/store-texts.md`](docs/store-texts.md) — the storefront owns the catalogue and the message syntax, Django asks it (`texts/storefront.py`) and refuses a save it cannot check; `texts/services.py` is the only writer; a save moves the cache generation and the `store_texts` surface. Read it before touching `texts/` or adding a text surface (emails).
- **Image uploads (`core/uploads.py`)**: see [`docs/image-uploads.md`](docs/image-uploads.md) — every image upload passes `validate_servable_image`: the media service's own per-format byte caps and pixel limit, vendored from its `contract/image-limits.json` (pinned, drift-checked by `.github/scripts/sync_upstream_sources.py`), never written down a second time. `ImageAndSvgField` (admin form and, through `CoreConfig.ready`, every `ModelSerializer`), TinyMCE and the builder's media library all call it; `FILE_UPLOAD_MAX_MEMORY_SIZE` is a memory threshold, not a size policy. A photo over its cap or the pixel budget is shrunk (`core/image_normalise.py`) rather than refused, and GPS is stripped from every raster. Read it before adding an upload path or a size limit.
- **Storefront page builder (`builder/`)**: see [`docs/builder.md`](docs/builder.md) — documents with drafts, immutable versions and releases (a publish is one release, a rollback another), validated against the storefront's block catalogue (`builder/storefront.py`; no catalogue, no save), `builder/services.py` the only writer, a release moves the cache generation and the `builder` surface, the public read is cached per release. Read it before touching `builder/` or adding a block rule.
- **allauth headless OpenAPI (`allauth-schema.yml`)**: see [`docs/allauth-schema.md`](docs/allauth-schema.md) — the storefront generates its all-auth parsers from it; `manage.py allauth_schema` writes it from allauth's own specification adapted to our adapter and settings, CI and the API-contract workflow check it, and `tests/integration/user/test_allauth_response_contract.py` holds our real endpoints to it. Regenerate it after touching `TenantHeadlessAdapter`, `ACCOUNT_SIGNUP_FIELDS`, the signup form or an allauth bump.
- **API error contract (`core/api/exception_handler.py`)**: see [`docs/error-contract.md`](docs/error-contract.md) — every raised error carries a stable `code` (and validation errors a per-field `fields`), codes are passed as `code=` and never through `_()`, and which modules are coded so far. Read it before adding a `ValidationError`/`APIException` a client has to react to.
- **Platform-wide documentation** lives in the sibling `grooveshop-docs/` repository (published at `docs.grooveshop.space`): architecture, multi-tenancy, end-to-end flows and operations under `src/dev/`, the bilingual tenant-admin guide under `src/admin/`. The files in this repo's `docs/` folder are copied into that site at build time, so keep editing them here. A behaviour change that a docs page describes ships with the doc change.
- **Client IP and throttle identity (`core/client_ip.py`)**: never read `REMOTE_ADDR`, `X-Forwarded-For` or `X-Real-IP` directly to identify a caller; use `trusted_client_ip(request)` or `client_ip_or_peer(request)`. Read [`docs/client-ip.md`](docs/client-ip.md) before touching throttles or anything keyed on an address.
- **Transactional email rendering (`core/templates/emails/**`)**: admin-authored WYSIWYG/HTML model fields (e.g. `PayWay.instructions` — a dedicated `tinymce.models.HTMLField`, picked up by `BaseModelAdmin.formfield_overrides` rather than a blanket `TextField`→`WysiwygWidget` override, so it holds HTML) must render as `{{ field|safe }}` in `.html` templates and `{{ field_text|safe }}` in `.txt` templates, where `field_text` is pre-built in the email task via `unescape(strip_tags(field))`. Django **autoescapes `.txt` templates too**, so the stripped plain text must be marked `|safe` or it re-encodes `& < >` back into entities. Escaping such a field (e.g. `|linebreaksbr`) renders literal `<div>` tags to the customer.
- **Rich text (`core/fields/rich_text.py`)**: every admin-authored HTML column is a `RichTextField`; its `pre_save` refuses content the policy would lose, sanitises, drops headings that show nothing, and records each uploaded image's real size as `data-natural-width`/`data-natural-height` (never in `width`/`height`, which are the author's layout). `manage.py normalise_rich_text` backfills. See [`docs/rich-text.md`](docs/rich-text.md).
- **Order emails (`order/emails.py`)**: each order email is an `EmailType` declared there, with its `build_context` and `sample`; the sending task calls `send_email` and the admin email preview (`emails/preview.py`) calls `emails.render.render` for the same type, so a task never builds its own message. A subject is a msgid on the type, nowhere else. Read lines and other translated rows inside the builder's `translation.override` (parler fixes a model's language when it is created). Marketing mail (re-engagement, abandoned cart, product alerts, the review reminder `order.review_request` sent `REVIEW_REQUEST_DELAY_DAYS` days after delivery) is a `Kind.MARKETING` type, and `EmailOptOut` is its one opt-out gate: `send_email` reads it, no task filters on `UserAccount.marketing_opted_out_at` (account state only). A customer lifts an opt-out through `PATCH /api/v1/user/email-preferences` (`user.services.subscription.set_marketing_preferences`, the only lifting writer; staff only record), and an alert by a signed-in customer who opted out is a `409 email_opted_out`. A guest's alert is a double opt-in (`product/alerts.py`): every guest request answers the same `202`, the alert starts INACTIVE and is activated by a POST of the signed, store-scoped token in its confirmation email, which also lifts that address's opt-out of the alert's type. See `docs/order-system.md` §6 and `docs/emails.md`.
- **Email pipeline (`emails/`)**: see [`docs/emails.md`](docs/emails.md) — the `EmailType` registry, `send_email` (gates, the store's switch, recipients, marketing opt-out, headers, header safety), `EmailSwitch`/`EmailOptOut`, `EmailLog` (a row for every send, skip and failure, written by `emails/log.py`: a keyed hash and a masked address, never an address or a body; `EMAIL_LOG_RETENTION_DAYS`), and the golden files that pin every order email as it is sent. `emails.transport` builds and sends the pipeline's messages, and `tests/unit/emails/test_only_transport_sends.py` fails for any other module that builds a message or calls `send_mail`/`mail_admins`. Every domain declares its types in `<app>/emails.py` (order, product, giftcard, b2b, contact, user, cart, the ops alerts, and allauth's 19 mails in `user/emails.py`, and the platform's own `platform.*` types in `tenant/emails.py` and `core/emails.py`, sent from `public`) through `emails.declare`, each move keeping `tests/integration/emails/golden/` equal. Read it before adding or changing an email.
- **Translation cache**: `PARLER_ENABLE_CACHING` is off. parler's Redis copy was slower than the Postgres row it copies (a prefetched translation was SET once per object on every request) and a queryset `.update()` bypassed its invalidation. Anything that lists translated rows prefetches them: `with_translations()`, and in the admin the model's own translations are prefetched by `BaseModelAdmin` while `prefetch_translations = ("product__translations",)` names related rows a column or `__str__` reads; list-filter dropdowns use `admin.filters.RelatedDropdownFilter`, never Unfold's. `tests/unit/admin/test_changelist_query_growth.py` fails for an admin that misses one.
- **Translations**: django-parler `TranslatableModel` on Product, BlogPost, Category, LoyaltyTier, etc. Languages: el (default), en. Factories create translations for all languages.
- **Audit history**: django-simple-history on models
- **Tree structures**: django-mptt `TreeForeignKey` for ProductCategory, BlogCategory
- **Monetary fields**: django-money `MoneyField` for prices, totals. Default currency: EUR
- **Stock management**: `StockManager` with atomic `reserve_stock()`/`release_reservation()` using `select_for_update()` to prevent overselling under concurrent requests. `StockReservation` model with TTL (the store's `STOCK_RESERVATION_TTL_MINUTES`). `StockLog` for audit trail.
- **Computed properties**: Models check `__dict__` for annotation values before falling back to DB queries (e.g. `likes_count`, `review_average`). A product's `likes_count`, `reviews_count` and `review_average` are correlated subqueries (`product/managers/product.py`), never `Count`/`Avg` joins: an aggregate join puts every other annotation into the GROUP BY, and `with_offer_kind`'s promotion subplan then ran once per joined favourite x review row (a 12-product listing took 1.9 s instead of 0.05 s). Add no aggregate join to a queryset that also carries `with_offer_kind`; `tests/unit/product/managers/test_product_count_annotations.py` fails on a `GROUP BY`.
- **Meilisearch indexing**: Models inherit `IndexMixin` with `MeiliMeta` class defining filterable/searchable/sortable fields, ranking rules, synonyms, typo tolerance. `meili_filter()` controls indexing eligibility. `get_additional_meili_fields()` adds computed fields.
- **Greeklish search**: handled at *index time* (`search/transliteration.py`); queries reach Meilisearch verbatim and are never rewritten into variants. Read [`docs/search/greeklish.md`](docs/search/greeklish.md) before touching transliteration, `MeiliMeta` search settings or `search/views.py`.
- **Product search facets**: [`docs/search/facets.md`](docs/search/facets.md) — disjunctive counts (`FacetGroup`), the `sidebarFacets` ranges (`StatsBaseline`) and what counts as a search for analytics. Read it before changing how `search/views.py` builds facets.
