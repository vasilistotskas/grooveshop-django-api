# Test configuration

How the pytest suites are set up and what that means for a test you write
or a run you start. Source: `pyproject.toml` (`[tool.pytest.ini_options]`,
`[tool.coverage]`), `tests/settings.py`, `tests/conftest.py`,
`tests/migration_seed.py`, `tests/cache.py`, `tests_mt/conftest.py`. The
code wins over this page.

Tests in `tests/` with `unit/`, `integration/`, and `utils/` subdirectories.

Settings read while Django sets up live in `tests/settings.py`, selected with `--ds=tests.settings` in `addopts` (the option outranks a `DJANGO_SETTINGS_MODULE` env var, which every container gets from `env_file: .env`). It pins `DISABLE_CACHE`, `ENABLE_DEBUG_TOOLBAR`, `APPEND_SLASH`, `DEBUG` and `DATABASE_BACKUPS_ENABLED` in the environment before `src/settings.py` loads, so the developer's `.env` cannot make a local run differ from CI, and declares `CACHES` as `tests.cache.WorkerScopedCache` (Redis, `clear()` scoped to its own `KEY_PREFIX`). The cache prefix and the per-run `MEDIA_ROOT` both follow `TEST_NAMESPACE` — the test database name plus the xdist worker — so two sessions on one machine never touch each other's state **as long as they use different `DB_NAME`s**: a second `-n N` run beside a full run must set its own `DB_NAME=…` (or use `-n0`), or it truncates the full run's `test_<DB_NAME>_gwN` databases. pytest-django imports `conftest.py` only after `django.setup()`, so a value assigned there is too late for anything an `AppConfig.ready()` or the cache registry reads. Key `conftest.py` settings:

**Which test databases survive a run** (`tests/db_lifecycle.py`, imported by both conftests): `--reuse-db` keeps the databases of the configured `DB_NAME` only (the one `.env` sets, or the settings default when there is no `.env` and no `DB_NAME` in the environment). A run under any other `DB_NAME` drops its `test_<DB_NAME>_gwN` (or `test_mt_<DB_NAME>`) databases when the session ends, so a parallel run costs a cold migration replay and leaves nothing behind. A run killed before its session ends still leaves its set; list what is left with `docker exec postgresql_db psql -U postgres -Atc "select datname from pg_database where datname like 'test\_%'"` and drop a set with `dropdb --force` once nothing is connected to it. The leftovers are not just disk: every table and index of every database holds an entry in Postgres's cumulative statistics, which live in `/dev/shm`. 854 leftover databases exhausted the dev container's 512 MB `/dev/shm` on 2026-11-02 and crashed a backend (`could not resize shared memory segment ... No space left on device`); `infra.compose.yml` now gives it 1 GB.
- MD5 password hasher (faster than default)
- `MEILISEARCH["OFFLINE"] = True`
- `CELERY_TASK_ALWAYS_EAGER = True` with `EAGER_PROPAGATES` — a task body that fails raises into the test
- `tests/` is the single-store suite: it runs in the public schema and makes its own tenants, so an autouse fixture (`_tests_run_as_one_store`, `tests/conftest.py`) answers `emails.send`'s "which store is this?" with a row-less stand-in; nothing else reads it, and a test that binds a store row (`tests.utils.staff.bind_store_tenant`) keeps that row. A test proving `StoreRequired` restores the real `bound_tenant` and binds none. Real per-store binding is `tests_mt`'s. An eagerly applied `TenantTask` runs in the schema it was dispatched in, as in production: `apply_async` stamps `connection.schema_name` as `_schema_name` and `TenantTask.__call__` binds that store's row from `request.headers` (pinned by `tests/unit/tenant/test_tenant_task_binds_its_store.py`)
- `transaction.on_commit` runs callbacks at once in non-transactional tests, exactly like Django's autocommit branch: an exception propagates unless the callback was registered `robust=True`. A test that means "this failure does not reach the caller" must say so (`pytest.raises(Retry)` in the task, a patched `apply_async`), not rely on a swallowed error
- **Migration seeds survive every flush** (`tests/migration_seed.py`): when `migrate` builds a test database, every non-empty table is snapshotted into the `test_migration_seed` schema; a `flush` (the end of any `transaction=True` / `TransactionTestCase` test) and a reused database at session start restore it. Every test therefore sees exactly the seeded rows — never a hand-maintained reseed. A test that needs a table without its seed deletes it inside its own transaction (`setUpTestData`, or the test body), never in a session fixture. A database built before this existed needs one `--create-db`. New migrations on a reused database first restore the old snapshot, so leftovers are never snapshotted. `available_apps`, `serialized_rollback` and `reset_sequences` bypass the restore and are refused at collection
- **The test database has the public schema only**: `tests/conftest.py` runs django-tenants' `migrate` with `shared=True`, so the seeded `webside` tenant's schema is not migrated too (it halved the time to build a worker database). No test in `tests/` needs a physical tenant schema; `tests_mt/` provisions its own
- `transaction=True` / `TransactionTestCase` only where real commits are the point (threads on other connections, `select_for_update` contention, `database_sync_to_async`); each one ends with a full-table flush
- `bind_tenant` (connection.tenant; restores `schema_name`) and `bind_tenant_and_schema` (also points `schema_name` at the tenant) — no local copies; `tests.utils.staff.store_tenant` builds a `Tenant` row (no schema: `auto_create_schema` is off for the whole suite)
- `openapi_schema` session fixture: the document `manage.py spectacular` writes, built once
- WebSocket tests drive the ASGI application with `asgiref.testing.ApplicationCommunicator` and raw `websocket.*` events (`tests/unit/asgi/test_websocket_stack.py`). Do not import `channels.testing`: its `__init__` imports `daphne.testing`, and neither daphne nor Twisted is a dependency
- `requires_meilisearch` marker for tests needing a live engine; `tests/utils/meilisearch.py` indexes real documents for them
- Query counts: Django's `CaptureQueriesContext` and pytest-django's `django_assert_num_queries` / `django_assert_max_num_queries`
- Coverage minimum: 70% (`fail_under = 70`, enforced on the combined CI shards), per-test timeout: 600s on the test body only (`timeout_func_only`): fixture setup is excluded, because pytest-timeout would otherwise charge a session fixture, such as a full tenant schema build, to whichever test triggers it. The multi-tenant lane's first test paid for three schema builds that way, 366 s on one CI run and over 600 s on another. A hung fixture is bounded by the CI job's `timeout-minutes`, and locally by nothing

**Network access.** `addopts` carries `--disable-socket --allow-hosts=...` (pytest-socket), so a test may `connect()` only to the local services the suite runs on: `127.0.0.1`, `localhost`, `::1` and the compose service names `db`, `redis`, `rabbitmq`, `meilisearch` (CI reaches PostgreSQL, Redis and Meilisearch on `127.0.0.1`/`localhost`). Any other connection raises `SocketConnectBlockedError`, a `RuntimeError`, so it is not swallowed by an `except OSError` or a requests error handler. That error in a test means the code under test called a real third party (a payment provider, a carrier, Resend, Cloudflare, Meta): mock the client at its boundary, as the neighbouring tests for that integration do. Never add a third-party host to `--allow-hosts`, and never use `@pytest.mark.enable_socket` or the `socket_enabled` fixture: local services are already allowed, and the marker removes all blocking for the test. xdist workers and `tests_mt` read the same `addopts`. An `except Exception` or an `except RuntimeError` around the call also hides a blocked attempt (`src/order/views/viva_webhook.py` has two such handlers), so a test of a failure path should assert the mocked client was the one called.

On Windows with Docker Desktop a fresh connection to `localhost` can stall 1-30 s (its IPv6 port relay); test durations that are exact multiples of ~30 s mean that, not slow code — run locally with `REDIS_HOST=127.0.0.1`.

**MT (multi-tenant) lane** — `tests_mt/` is a SIBLING of `tests/`, not a subdirectory: `tests/conftest.py` strips multi-tenancy (`DATABASE_ROUTERS = []`, no `TenantMainMiddleware`) to keep the main suite fast, which makes schema-binding bugs (cross-schema FKs, cache-key leaks, seed migrations that stop reaching new tenants) invisible to it. `tests_mt/conftest.py` keeps the real `TenantSyncRouter` and `TenantMainMiddleware`, provisions two tenant schemas per session (`mt_smoke`, `mt_smoke_b`; the fixtures `mt_tenant` and `mt_tenant_b` return them), and runs its tests on top. Not collected by a bare `uv run pytest` (`testpaths = ["tests"]` excludes it) — run it explicitly with `uv run pytest tests_mt -n 0` (serial; schema switching is process-global via `connection`, and each xdist worker would build its own database with every schema).

Building the schemas is nearly all of the lane's time: each is a full migration replay. The test database is created with the public schema only; the session fixture `mt_store_schemas` then creates the two tenants' rows and empty schemas and migrates them and the seeded `webside` at the same time with django-tenants' `subprocess` executor (one `manage.py migrate_schemas --schema <name>` process per store). Those processes get `DB_NAME` set to the test database and do not see what `tests_mt/conftest.py` assigns to `settings`, so a migration that needs such a setting must get it from the environment (`MEILI_OFFLINE` is passed that way). Run the lane from the repository root: the executor starts `manage.py` from the working directory.

**What to run before pushing.** A small PR runs the static gates (`ruff check`, `ruff format`, `ty check`, `lint-imports`) and the tests of the code it touched; CI runs the full suite on the pull request (a docs-only pull request runs only change detection and the `CI Gate` check, the one check branch protection requires; see the CI/CD section of `CLAUDE.md`). A full local run is for a wide change (settings, a `conftest.py`, a shared base class, moved code) or for when CI is unavailable, and it needs its own `DB_NAME` beside any other session (above).

**Refreshing `.test_durations`.** pytest-split cuts the suite into the CI shards from the committed `.test_durations`, and a test missing from it is weighted at the average. The timings come from CI, never from a local run (a developer machine balanced the shards within 0.7% on paper and they ran 9 to 16 minutes): each shard records the tests it ran and uploads `test-durations-shard-<n>`, and the Coverage Gate job merges them into one artifact, `test-durations`. To refresh, take a green pull_request run of the code as it is now and commit its file:

```bash
gh run download <run id> --name test-durations --dir /tmp/durations
cp /tmp/durations/test-durations.json .test_durations
```

(`python .github/scripts/merge_test_durations.py --run-id <run id>` does the same from the per-shard artifacts.) Refresh after a change that moves every test's cost (the worker count, how the database is built) and when the "Run Tests (shard)" steps of one run differ by more than about 20%. A shard cannot be shorter than its longest file, since `--dist loadfile` keeps a file on one worker: when one shard stays slow after a refresh, look at that file, not at the split. Changing the shard count means changing the matrix, `--splits` and the merge step's `--shards` in `ci.yml` together.
